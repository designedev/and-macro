# 0.3.1 — OCR 실행 준비 및 활성 창 오판 수정

검증일: 2026-10-03, Asia/Seoul.

## 사용자 재현 흐름

새 매크로 → 찾을 문구 ‘입장하기’ → 시작 → 게임으로 이동 → ‘현재 앱에서 실행’ → 반응 없음.

기존 코드에서 반응 없이 끝날 수 있는 세 경로를 확인해 0.3.0으로 수정했습니다. 이후 사용자 재현과 `ScreenMacro` 로그에서 READY → WINDOW_UNAVAILABLE → STOPPED를 확인했습니다. 실제 오류는 OCR 실행 전 활성 창 검사에서 발생했습니다.

1. 오버레이는 실행 버튼을 먼저 비활성화했지만, 서비스는 초기화 중 실행 요청을 무시했습니다. 초기화가 끝나도 버튼을 다시 활성화하지 않았습니다.
2. 인식 결과의 1초 제한을 세션 검증에 포함해 최초 OCR이나 느린 OCR 결과를 인식 테스트에 표시하기 전에 세션을 종료했습니다. 문구가 없는 결과까지 같은 이유로 종료할 수 있었습니다.
3. 새 프레임 수신의 4초 제한시간이 코루틴 취소로 전파되면, 실행 작업만 종료되고 캡처 서비스와 비활성화된 버튼이 남을 수 있었습니다.

## 실기기에서 확인한 활성 창 차단 원인

게임의 접근성 창은 활성·초점 상태이고, WindowManager도 게임을 전면의 전체 화면 앱으로 표시했습니다. 초기 조회에서 다음 창들이 함께 보였습니다.

| 창 | 접근성 종류 | 계층 | 범위 |
|---|---|---|---|
| 마비노기 모바일 본문 | APPLICATION | 0 | (0, 0)–(1080, 2340) |
| 게임 내부 보조 창 | APPLICATION, 게임 창의 자식 | 1 | (0, 112)–(1, 2340) |
| 상태 표시줄 | SYSTEM, 비활성·초점 없음 | 2 | (0, 0)–(1080, 112) |
| 접근성 버튼 | SYSTEM, 비활성·초점 없음 | 3 | (889, 1324)–(1080, 1515) |

기존 검사는 다른 APPLICATION 창 또는 게임보다 높은 계층의 창이 하나라도 있으면 전체 실행을 거부했습니다. 따라서 상태바와 접근성 버튼, 게임 자체의 1px 자식 창만으로도 실패했습니다.

0.3.1에서는 같은 앱의 확인된 자식 창과 비활성 시스템 창을 전체 차단에서 분리하고, 그 창의 사각형이 덮는 부분만 인식·클릭에서 제외합니다. 키보드, 관련 없는 앱 창, 활성·초점이 있는 시스템 창은 계속 차단합니다. 전면 앱·창이 바뀌면 세션을 종료합니다. 전체 화면을 덮는 시스템 창은 전체 검색 영역을 제외하므로 클릭 후보를 만들지 않습니다. Android가 제공하는 창 메타데이터와 좌표를 사용하며 패키지 허용 목록은 추가하지 않았습니다.

창 목록은 순간적으로 변할 수 있습니다. `outputs/device-window-layout.txt`는 후속 조회 시점의 목록이며 초기 1px 자식 창 대신 일시적인 UNKNOWN 유형 창이 보일 수 있습니다. 초기 진단에서 확인한 배치를 `WindowPolicyTest`로 재현했습니다.

## 변경

- 전체 화면 캡처 크기 확인과 한국어·영어 OCR 준비가 완료된 뒤 실행·테스트·등록 버튼을 활성화합니다. 서비스가 요청을 수락한 경우에만 버튼을 비활성화합니다.
- 캡처·앱·창·좌표 검증과 프레임 신선도 검증을 분리했습니다. 창 전환, 회전, 화면 잠금, 캡처 종료에 대한 정지는 유지합니다.
- 실행에서 1초를 초과한 유일 후보는 클릭하지 않고 버린 뒤 새 프레임으로 다시 인식합니다. 클릭 전 대기 이후와 실제 제스처 전달 게이트에도 신선도 검사를 적용합니다. 지속적으로 느리면 오버레이에서 검색 영역을 줄이도록 안내합니다.
- 클릭 없는 인식 테스트는 느린 결과도 표시합니다. 찾을 문구, 정확 일치/포함 조건, 읽힌 문구 목록, 처리 시간, 검출 결과를 확인할 수 있습니다. OCR 원문은 테스트 화면 메모리에서만 유지하고 실행 로그에 기록하지 않습니다.
- 새 프레임 수신 실패를 일반 인식 오류로 처리합니다. 실행 중 3회 연속 오류면 세션을 종료합니다. 인식 테스트·화면 등록의 오류도 명시적으로 세션을 종료합니다.
- 오류 정지 이유는 짧은 알림과 앱 상태 카드에 표시합니다. debug 빌드의 상태·결과 코드·처리 시간·정지 이유는 Logcat `ScreenMacro` 태그에도 기록합니다. 화면 이미지와 OCR 원문은 Logcat에 기록하지 않습니다.
- 정확 일치 기본값, 클릭 간격, 단일 활성 창, 특정 패키지 제한 제거, 기존 Room DB 구조는 유지했습니다. 사용자 매크로와 이미지를 삭제하지 않습니다.

0.3.1에서 사용자가 정상 동작을 확인했습니다. 실제 단말기 로그에서 14:11:11 인식 테스트의 MATCH_UNIQUE(219ms)와 클릭 없는 완료를 확인했습니다. 14:11:32와 14:11:35 실행에서 MATCH_UNIQUE(256ms/360ms), 터치 전달 및 GESTURE_COMPLETED를 각각 확인했습니다. 특정 시점의 실제 게임·기기 동작 확인이며 모든 게임 화면이나 Android 17 전체의 호환성을 보장하지 않습니다.

진단 중 사용한 UI 덤프 도구는 접근성 서비스를 일시적으로 중단할 수 있었습니다. 따라서 당시 ‘접근성 서비스를 활성화하세요’ 문구를 원래 실패 원인으로 단정하지 않았습니다. 이후 실제 단말기의 진단은 접근성을 중단하지 않는 상태 조회와 앱 자체 메타데이터 로그만 사용했습니다.

## 확인 순서

기존 매크로 → 인식 테스트 → 전체 화면 캡처 동의 → 게임의 ‘입장하기’가 보이는 화면 → 준비 완료 → 현재 앱에서 인식 테스트.

- 읽힌 문구가 ‘입장하기’이고 유일 후보: 캡처·OCR 위치 확인 후 실행으로 실제 제스처 반응을 확인합니다.
- 문구가 다른 형태로 읽힘: 표시 결과를 근거로 검색 영역 또는 문구 조건을 검토합니다. 정확 일치 조건을 임의로 포함 일치로 변경하지 않았습니다.
- 1초 초과: 버튼 주변으로 검색 영역을 줄이고 다시 테스트합니다.
- 읽힌 문구 없음: 테스트 캡처 이미지·검색 영역·오버레이 위치를 확인합니다.
- 창 또는 캡처 오류: 표시된 오류와 Logcat 메타데이터를 근거로 해당 경로를 조사합니다.
